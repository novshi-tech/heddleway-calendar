# 0001 カレンダーの統合ビューと同期は、Heddleway の外の別ツールとして作る

- 状態: 案(2026-11-10、直樹とのディスカッション)。2026-11-11: 別ツールで進める方向になった。前提条件の決定 4 は Heddleway の `docs/adr/0008`(案)に書いた。Webhook を最初から使うことにした(決定 5)。0008 が採用されるまで、この ADR も案のまま
- 関連(novshi-tech/heddleway):
  - `docs/adr/0004`(1 つのデプロイ = 1 つの組織。複数のデプロイを Claude に並べてつなぐ)
  - `docs/adr/0005`(Murmur = トピック索引をゲートウェイの機能として持つ)
  - `docs/adr/0008`(アプリには、使える口を絞った許可を出す。案)
  - `docs/concept.md`(ゲートウェイはメソッドやパスで認可しない)
  - `murmur/docs/adr/0012`(本体は外に何も書かない)、`0018`(1 人が複数の組織にまたがる対応はしない)、`0022`(Murmur 間連携の構想)、`0026`(自分専用の Murmur は作らない。横断は巡回)

## 背景

複数の組織で仕事をする人は、組織の数だけカレンダーを持つ(Google Workspace、Microsoft 365)。困ることは 2 つ。

1. 自分の予定を 1 か所で見られない
2. ある組織の同僚からは、別の組織の予定が見えない。空いているように見えて、予定を入れられる

Heddleway は組織ごとにデプロイし(0004)、各デプロイがその組織のカレンダー(Google Calendar、Graph の予定表)への接続を持っている。これを使って、次の 2 つをするツールを作りたい。

- **統合ビュー**: 複数の Heddleway のデプロイに OAuth でつなぎ、それぞれのカレンダーをまとめて 1 つの画面に出す
- **同期**: あるカレンダーの予定を、ほかのカレンダーに「予定あり」として写す

元の予定を作る・変えるのは、エージェント(スタンド)が各組織のコネクタとカレンダーのスキルで行う。ツールは予定の編集画面を持たない。トピック索引が「送信はスタンド、本体は記録だけ」としているのと同じ分担。

作る場所に 2 つの案がある。

- **A. 別のツール(このリポジトリ)**: Heddleway の外に置き、複数のデプロイの OAuth クライアントになる
- **B. Heddleway に内蔵する**: トピック索引と同じように、カレンダーをゲートウェイの機能にする。予定も 1 つのトピックと言えるので、筋は通っている

## 決定(案)

### 1. A を採る。Heddleway の外の別ツールとして作る

理由は 3 つ。

**(1) B では、やりたいことが 2 つとも機能の外に出る。**
内蔵の機能は 1 つのデプロイの中で動き、ほかの組織のデプロイは見えない(0004 の決定 1。組織の切り替え・テナントの概念は足さない)。だから B にすると、組織をまたぐ統合ビューも同期も機能にはできず、どちらもエージェントの仕事になる。内蔵のカレンダーに残るのは「1 つの組織の予定を見る」ことだけで、それは Google や Outlook の画面がすでにやっている。

**(2) 同期は、エージェントの仕事に向かない。**
- 同期の目的は、同僚が予定を入れようとしたときに、もう埋まって見えること。エージェントが動いたときしか写らないなら、その間は空いて見える。定期実行で縮められるが、判断の要らない機械的な処理に毎回エージェントを起こすことになる
- 0004 の決定 4 は「ある組織で読んだものを別の組織に書くときは、ユーザーに確認する」。エージェントが同期すると、この約束に常設の例外を作ることになる。機械的に「時間帯だけ」を写す専用の経路を別に持つほうが、約束を崩さない
- 写しの対応(どの予定の写しがどれか)と、消えた予定の後始末は、状態を持つ仕組みのほうが確実

**(3) 多くの人には要らない。**
組織をまたぐカレンダーの同期が要るのは、複数の組織に属する人だけ。Heddleway は「Murmur なしでも動く」(0005)くらい中核を軽く保っているので、少数のための機能を中に入れない。

**位置づけ(2026-11-11)**: このツールは、Heddleway の「アプリ」(0008)の 1 つ目になる。アプリは、スタンドではないクライアントで、使える口を絞った許可でつなぐ、決まった処理をするツール。エージェントは万能だが、コストがかかり、結果が揺らぎ、動いているときしか働かない。判断の要らない処理は、アプリに任せる。汎用の部分(絞った許可)は Heddleway に入り、少数の人のための部分(カレンダーの同期)はここに置く。

### 2. B のうち「予定をトピックとして扱う」は、この決定と別の話として残す

「予定も 1 つのトピック」は、トピック索引のリストにカレンダーを足す話(会議の準備や後始末を、その予定のトピックで追う)。1 つの組織の中で閉じていて、同期とは関係がない。やるならトピック索引のコネクタとして Heddleway の側で決める。このツールとは競合しない。

### 3. 組織の境界をまたぐのは「時間帯」だけ

このツールは、Murmur の 0026 が採らなかった「チームの境界の外にある、本人だけの集約点」と同じ位置に立つ。0022 はそれを「組織の管理者から見ると情報の脱出口」と書いている。カレンダーで採ってよいと考える理由と、守る線を決めておく。

- **ほかの組織に書くのは、開始と終了の時刻だけ。** 写しの件名は固定(「予定あり」)。本文・場所・出席者・添付・会議の URL は写さない。公開の設定は非公開にする
- **予定の中身を保存しない。** 持つのは、写しの対応(元のデプロイと予定の ID、写した先のデプロイと写しの ID、時刻、変更の検知に使う値)だけ
- **統合ビューは、その場で読んで出す。** 本人がサインインして開いたときに各デプロイから読み、保存しない。中身(件名など)が見えるのは本人だけ
- **写しを写さない。** 写しにはこのツールの印を付け(Google は拡張プロパティ、Graph は拡張)、印のある予定は元として扱わない
- **元の予定は書き換えない。** このツールが書くのは、自分が作った写しだけ(作る・時刻を直す・消す)

0026 が集約点を採らなかったのは、要約という「中身」を境界の外に集めるから。ここで境界を越えるのは時間帯だけで、空き時間の共有は、組織をまたぐ日程調整で普通に行われている範囲に収まる。0026 の「横断の俯瞰は思ったほど要らなかった」はタスクの話で、予定は 1 人の 1 本の時間軸なので、組織ごとに分けて見ることができない。

### 4. Heddleway に足してもらうもの: 使える口を絞った許可(Heddleway の 0008)

いまの Heddleway の許可はスコープが 1 つで、OAuth でつないだクライアントは、本人がつないでいるどのサービスにも届く(メール、会計も)。このままだと、このツールが預かるリフレッシュトークンは、カレンダーの同期には広すぎる。

- Heddleway の 0008 で、アプリに「使える口」(サービス・メソッド・パスの組)を絞った許可を出す。組織の管理者がアプリを登録し、本人が同意する
- サービスの単位では足りない。Microsoft 365 は 1 つのサービス(`graph`)にメールも予定表も入っているので、パスまで絞る
- このツールは、口の定義(予定の一覧・差分・写しの作成と更新と削除・購読)を配る。管理者はそれを読んで登録する
- **これが前提条件。** 0008 が採用されないなら、複数の組織の全サービスに届くトークンを 1 か所に集めることになるので、このツールは作らない

絞れるのは口まで。カレンダーの口を許されたこのツールは、技術的には予定の中身も読める。決定 3 の線(時間帯しか写さない、中身を保存しない)は、このツールの規律で、ゲートウェイは強制しない。

### 5. つなぎ方と動かし方

- このツールは、各デプロイの OAuth クライアントになる(Claude のコネクタと同じ入口)。本人がデプロイごとにサインインして許可する
- 上流の API(Google Calendar、Graph)は、デプロイの中継を通して呼ぶ。上流のトークンはこのツールに来ない
- API の知識(予定の一覧、差分の取得、写しの作成)は、このツールが持つ。Heddleway は今までどおり API の仕様を知らない
- **Webhook で動く。** 予定は時間に関わるので、元の予定が変わったらすぐ写す。このツールが、中継を通して上流の購読(Graph のサブスクリプション、Google の通知チャネル)を作り、通知の宛先を自分の URL にする。購読の更新と後始末もこのツールがする。Heddleway は Webhook の受け口を持たない(0008 の決定 6)
- 定期実行は、取りこぼしの拾い直しと、購読の更新に使う
- 写す対象は、先の一定の期間にある、本人が「予定あり」になっている予定。辞退した予定・取り消された予定・「空き時間」の予定は写さない。繰り返しの予定は、期間の中の 1 回ずつに展開して写す

## 代案

- **B. Heddleway に内蔵する**: 決定 1 の理由で採らない。内蔵にしても、組織をまたぐ部分はエージェントに出る
- **C. 何も作らず、スキルだけにする**(エージェントが各コネクタを巡回して、統合ビューをその場で作り、同期のスクリプトを回す): 新しい常駐のサービスも、トークンの新しい置き場も要らない。スタンドはもともと組織が出会う場所(0004 の決定 6)なので、境界の面では一番きれい。ただし決定 1 の (2) のとおり、同期が間に合わない。**統合ビューだけならこれで足りる**ので、同期が要らない人にはこちらを勧める
- **D. Heddleway を通さず、Google と Microsoft に直接つなぐ**(市販のカレンダー同期サービスと同じ形): 組織ごとに OAuth のアプリの登録と管理者の同意が要る。Heddleway を通せば、組織がすでに認めた接続を使える。採らない
- **E. 市販のカレンダー同期サービスを使う**: 同期だけなら足りる。予定の中身に届く権限を外のサービスに渡すことになり、組織の管理者が認めないことが多い。Heddleway のデプロイがある組織では、このツールのほうが通しやすい

## 条件・リスク

- **Heddleway の 0008 が通らなければ、この ADR は不採用。** そのときは C(スキル)に倒し、このリポジトリは破棄する
- **組織の管理者が決められる。** このツールをつなげるのは、管理者がアプリとして登録したデプロイだけ(0008 の決定 1)。本人は各デプロイの許可の一覧から取り消せる
- Graph のサブスクリプションは、購読の対象がボディにあるので、パスでは予定表だけに絞れない(0008 の条件・リスク 2 と未決 1)。このツールは予定表しか購読しないが、それはこのツールの規律になる
- 通知の宛先の条件(Graph の宛先の検証、Google の通知チャネルの宛先)を、中継を通した購読で満たせるかは、まだ確かめていない。最初に確かめる
- 写しが残る事故(元が消えたのに写しが残る、同期を止めたあとに写しが残る)。接続を外すときに、そのデプロイに作った写しを消す手順を持つ
- 写しの時間帯から、ほかの組織での働き方(いつ会議が多いか)は分かる。これは本人が同期を有効にすることで受け入れる範囲とする
- 使う人が少ない。直樹のほかに使う人がいなければ、C で足りた、ということになる

## 未決

1. **どこにデプロイするか。** どの組織のものでもないので、本人の Cloudflare アカウントに 1 人 1 つ置くのが素直(Heddleway と同じ Workers + D1、TypeScript の想定)。複数人で 1 つを共有する形にするかは決めていない
2. 終日の予定、仮の予定(未回答)、非公開の予定を写すか。写す期間の長さ
3. 1 つのデプロイの中に複数のカレンダーがあるとき(共有カレンダーなど)、どれを元にし、どれに写すか。最初は各デプロイのメインのカレンダーだけ
4. 統合ビューの画面を、このツールの Web 画面にするか、エージェントが読める API だけにして画面はスタンドに任せるか(トピック索引は後者)
5. Heddleway の中継を呼ぶのに MCP を話すか(0008 の未決 4)
