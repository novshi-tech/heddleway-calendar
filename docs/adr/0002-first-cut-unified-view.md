# 0002 最初に作るのは、本人の予定の統合ビュー

- 状態: 採用(2026-11-27、直樹の「予定が横断的に見られないのが不便」から。範囲は直樹が選んだ)
- 関連: [0001](0001-separate-tool-across-instances.md)、Heddleway の `docs/adr/0008`(アプリの絞った許可。2026-11-13 採用、11-14 実装)

## 背景

0001 は統合ビューと同期の 2 つを決めた。前提の 0008 は採用・実装済みなので、作り始められる。どちらから作るか、0001 の未決のどこまでを決めるかを決める。

いま困っているのは「自分の予定を 1 か所で見られない」こと(0001 の背景の 1)。直樹の予定は 3 つの組織に分かれていて、3 つともゲートウェイにカレンダーの接続がある。

| デプロイ | 組織 | カレンダー |
|---|---|---|
| gateway.novshi-tech.com | ノブシテック | Google Calendar(`calendar`) |
| gateway.quzilla.co.jp | くじらキャピタル | Google Calendar(`calendar`) |
| gateway.urban-b.com | UBS | Microsoft 365 の予定表(`graph`) |

候補は、(a) 本人の予定の統合ビュー、(b) それにチームの空き状況とビルメンNEXT の定期作業・不在を足す、(c) 同期から作る、の 3 つだった。直樹が (a) を選んだ。

## 決定

### 1. 統合ビューを先に作り、同期はあとにする

- 統合ビューは読むだけで済む。口は予定の一覧の読み取りだけで、0008 の未決 1(Graph のサブスクリプションをパスで絞れない)にまだ触れない
- 同期は、この土台(デプロイへの接続、許可の更新、予定の読み取りと正規化)の上に足す

### 2. 画面はこのツールが持つ。モバイルファースト(0001 の未決 4)

- 見たいのはスマホで、エージェントを起こさずに開けること。サーバーで HTML を組んで返し、画面にスクリプトはない
- 今日から 7 日を、日ごとに時刻順に並べる。予定ごとに組織の色と表示名を付ける。前後の週へ移れる。PC はあとで崩さず広げる
- 0001 の決定 3 のとおり、開いたときに各デプロイから読み、予定は保存しない。D1 に持つのは接続(許可のトークン、使うカレンダーの認証情報の ID、表示名と色)だけ。トークンは暗号化して置く
- 別の組織の予定と時間が重なっている予定に「重なり」を付ける。組織をまたぐ二重予約は、どちらのカレンダーの画面でも見えないので
- 予定を押すと、そのカレンダーの画面(Google Calendar、Outlook on the web)を開く。予定を作る・変えるのはそちらか、エージェント(0001 の背景)

### 3. 本人のサインインは、このツール自身の OIDC。デプロイは直樹の Cloudflare に 1 つ(0001 の未決 1)

- Heddleway の OAuth の応答には、だれの許可かが入らない。だから、このツールに入れる人はこのツールが自分で確かめる。OIDC(Google か Entra ID)でサインインし、`ALLOWED_EMAILS` にあるアドレスだけを通す
- 接続はサインインしたユーザーごとに持つ。最初は直樹 1 人で、複数人で 1 つを共有する形は、使う人が出てから決める
- Workers + D1、TypeScript strict、フレームワークなし。Heddleway Room と同じ作り

### 4. 口(アプリの定義)は、メインのカレンダーの予定の読み取りだけ(0001 の未決 3)

| サービス | メソッド | パス |
|---|---|---|
| `calendar` | GET | `^/calendar/v3/calendars/primary/events$` |
| `graph` | GET | `^/v1\.0/me/calendarView$` |

- 定義は `/client.json`(クライアント ID の URL)の `heddleway_app` に載せる。各組織の管理者が `/admin/apps` にこの URL を入れて承認する
- 通る例と断られる例(ほかの人のカレンダー、メール、書き込み)を定義に付ける

### 5. 呼び方: MCP で `issue_token`、予定は REST の中継(0008 の未決 2・0001 の未決 5)

- アクセストークンでデプロイの `/mcp` を呼び、`issue_token` で 15 分のゲートウェイのトークンを受け取り、`/api/<service>/...` で予定を読む。0008 の決定 5(入口を増やさない)のまま
- カレンダーの認証情報の ID は、つないだときに `list_credentials` で取って持つ。ゲートウェイでカレンダーをつなぎ直して ID が変わったら、取り直す

### 6. 出し方(0001 の未決 2 のうち、ビューの分)

- 辞退した予定・取り消された予定、Google の勤務場所は出さない
- 未回答・仮承諾の予定は「仮」、空き時間の予定は「空き」、不在は「不在」として薄く出す。重なりの判定に「空き」は入れない
- 終日の予定と、1 日をまたいで覆う予定は、その日の頭に出す
- 非公開の予定も本人には件名ごと出す(見るのは本人だけ)
- 時刻は日本時間で固定する

## 未決

1. ビルメンNEXT の定期作業・不在、UBS の同僚の空き状況(getSchedule)を入れるか。入れると口が広がる(ビルメンNEXT の GraphQL は `POST /graphql` 1 本で、パスでは読み取りに絞れない)。入れるなら別の ADR で決める
2. 同期(0001 の本題)。Webhook の購読を中継で作れるかを最初に確かめる(0001 の条件・リスク)
3. 接続を外すときに、デプロイの側の許可も取り消すか。今はこのツールの側で消すだけで、デプロイの「アクセスを許可したアプリ」には残る
4. 使わない期間が 30 日を超えると許可が切れる(0008 の未決 3)。そのときは画面に「つなぎ直す」が出る
